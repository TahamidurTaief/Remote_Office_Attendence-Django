### MODULE 1 — AUTHENTICATION & SECURITY (`apps.accounts`)

#### 1. Business Purpose
Manages user identity, multi-method authentication, session isolation, brute-force protection, MFA, trusted devices, and role-based security policy enforcement. Root trust anchor for all modules.

#### 2. Business Workflow
1. User authenticates via email or phone+password.
2. `LoginProtection` evaluates failed-attempt history, lock levels, CAPTCHA requirement.
3. On success: `UserSession` created, `active_session_key` stamped on `CustomUser`.
4. `SessionDeviceMiddleware` enforces single-device login + 30-minute idle timeout.
5. `MFARequiredMiddleware` intercepts navigation if role requires MFA and user hasn't set it up.
6. `SuspendedEmployeeMiddleware` immediately logs out suspended employees mid-session.
7. `PasswordResetOTP` supports OTP-based password reset.
8. `WorkspaceLockEvent` tracks idle lock/unlock cycles per session.

#### 3. User Journey
- **Admin:** Creates user → assigns RBAC role → sets SecurityPolicy → enables MFA requirement.
- **Employee:** Logs in → optionally sets up TOTP → enters backup codes → trusts device → works within session.
- **Failed login:** Progressive 4-level escalating lock → CAPTCHA challenge.

#### 4. Dashboard Flow
- Admin dashboard: active sessions count, trusted devices count, recent audit events (last 24h).
- No dedicated security metrics panel — embedded in admin dashboard only.

#### 5. Approval Flow
- MFA setup: self-service, no approval.
- Role assignment: requires admin action (`UserRoleAssignment`).

#### 6. Database Entities

**Master Tables:** `Module`, `Action`, `Permission`, `PermissionDependency`, `Role`, `SecurityPolicy`, `ApprovalPolicy`, `ApprovalChainStep`

**Transaction Tables:** `CustomUser`, `UserRoleAssignment`, `UserPermissionOverride`, `RolePermission`

**History/Security Tables:** `UserLoginActivity`, `UserSession`, `TrustedDevice`, `PasswordResetOTP`, `LoginProtection`, `WorkspaceLockEvent`, `UserSecurityProfile`

#### 7. Timeline Integration
- ❌ No shared timeline events from auth events (login/logout/lock) to global `ActivityLog`.
- `WorkspaceLockEvent` is siloed — not surfaced in any dashboard timeline.

#### 8. Activity Log
- `UserLoginActivity` tracks login events → **NOT integrated with global `notifications.ActivityLog`.**
- Two separate logging systems exist side-by-side.

#### 9. Audit Log
- `notifications.AuditLog` exists as global sink. `log_audit()` helper available.
- **PROBLEM:** Auth events (login, logout, role changes, MFA enable/disable) are **NOT consistently written to `AuditLog`**. Critical compliance gap.

#### 10. Notification Integration
- `Notification.notif_type` includes `role_changed`, `permission_changed`.
- **PROBLEM:** No evidence role assignment changes or MFA enable/disable trigger `Notification` records.

#### 11. Reports
- ❌ No auth/security reports (login activity, failed login, session report, export).

#### 12. Analytics
- Raw counts in admin dashboard only. No trends, no export.

#### 13. Permissions
- **9-layer `PermissionEngine`** implemented: superuser bypass → employee status → role permissions → overrides → dependency chain → data scope → security policy → approval policy → business validation.
- DataScope hierarchy: `OWN < TEAM < DEPARTMENT < BRANCH < COMPANY < GLOBAL`.
- Permission caching via `_resolved_permissions_cache` on user object (request-scoped).
- **PROBLEM:** `MFARequiredMiddleware` uses legacy `request.user.role` CharField, not RBAC `UserRoleAssignment.role.code`. Dual authority on user role.

#### 14. API Dependencies
- All modules import `PermissionEngine.evaluate()`.
- `pyotp` for TOTP. Django email backend for OTP.

#### 15. Offline Requirements
- ❌ Authentication is entirely online. No offline token mechanism.

#### 16. Security Considerations
- **CRITICAL:** `DEBUG = True` in [settings.py](file:///c:/Users/ISSL/Desktop/Remote_Office_Attendence-Django/fieldtrack/settings.py#L12) — must be `False` in production.
- **CRITICAL:** `SECRET_KEY` falls back to hardcoded insecure string if env var not set.
- **CRITICAL:** `EMAIL_HOST_USER` / `EMAIL_HOST_PASSWORD` are empty — email non-functional.
- PIN stored as plain SHA256 (no salt) — susceptible to rainbow table attacks.

#### 17. Missing Features

- ❌ JWT / API key authentication layer

### MODULE 2 — EMPLOYEE MANAGEMENT (`apps.employees`)

#### 1. Business Purpose
Full employee master data management, lifecycle state machine, org hierarchy, document management, asset assignment, and manager delegation.

#### 2. Business Workflow
1. HR creates `Employee` in `DRAFT` via 7-step wizard (basic → org → salary → user → documents → emergency → assets).
2. Completion percentage tracked (5 × 20% = 100%).
3. `DRAFT → PENDING_APPROVAL` (low-risk, immediate).
4. `PENDING_APPROVAL → ACTIVE` requires `LifecycleTransitionRequest` approval (high-risk).
5. Further lifecycle: Active → Probation → Confirmed → Suspended/Resigned/Terminated → Archived.
6. Archived is terminal — read-only.
7. Manager can delegate approval authority via `ManagerDelegation`.

#### 3. Approval Flow
- `LifecycleTransitionRequest` model — HIGH_RISK transitions queue for admin approval.
- LOW_RISK transitions apply immediately (draft→pending_approval, probation→confirmed, etc.).
- `reviewed_by`, `reviewed_at`, `review_note`, `effective_date` captured.
- **PROBLEM:** No notification triggered on `LifecycleTransitionRequest` create or review.

#### 4. Database Entities

**Master Tables:** `Department`, `Designation`, `DocumentType`, `AssetType`, `AssetCondition`

**Transaction Tables:** `Employee`, `EmployeeProfile`, `EmployeeLeaveRule`, `EmployeeDocument`, `Asset`, `AssetAssignment`, `ManagerDelegation`, `LifecycleTransitionRequest`

**History Tables (Immutable):** `EmploymentHistory`, `EmployeeAuditLog`

**Activity Table:** `EmployeeActivityLog`

**Location Table:** `EmployeeLocationSync`

#### 5. Critical Architecture Problem — Dual Employee Model
> [!WARNING]
> **Two employee records exist per person:**
> - `Employee` (master): lifecycle state, payroll, org structure, documents, assets.
> - `EmployeeProfile` (legacy/operational): linked to CustomUser, used by Attendance/Leave/Expense/Projects.
> - `EmployeeProfile.department` and `.designation` are plain `CharField` — NOT FK to normalized `Department`/`Designation` models.
> - Every query needing org data must join both models via `master_employee` OneToOne link.

#### 6. Missing Features
- ❌ Notifications on lifecycle request create/review
- ❌ EmploymentHistory writes not guaranteed on all transitions
- ❌ Module-local logs not wired to global ActivityLog/AuditLog
- ❌ No exportable employee reports (turnover, headcount trend)
- ❌ `OrgHierarchyService.get_all_subordinates()` loads ALL employees into Python memory → **O(n²) performance problem**
- ❌ No payroll calculation engine
- ❌ No performance review / KPI module
- ❌ `ManagerDelegation` not checked in any approval routing visible in code

### MODULE 3 — ATTENDANCE & GPS TRACKING (`apps.attendance`)

#### 1. Business Purpose
Captures check-in/check-out events (office and field), geofence validation, GPS tracking, overtime, and attendance correction workflows.

#### 2. Business Workflow
1. Employee checks in via PWA (GPS captured, photo optional).
2. Geofence check → `type` (office/field), `gps_quality`.
3. OfficeSchedule evaluated → `status` (on_time / late).
4. Background GPS pings every `tracking_interval` minutes.
5. Checkout → `total_hours`, `overtime_minutes`, `is_early_checkout` computed.
6. Forgot checkout → `ForgotCheckoutRequest` (2-step: manager then HR).
7. Incorrect times → `AttendanceCorrectionRequest` (1-step).
8. Daily cron marks absences.
9. 3-month retention: old records marked `is_expired=True`.

#### 3. Database Entities

**Master Tables:** `AttendancePolicy` (branch-level or global)

**Transaction Tables:** `Attendance`, `AttendanceLocation`, `AttendanceAbsentLog`, `ForgotCheckoutRequest`, `AttendanceCorrectionRequest`

**Sync/Operational Tables:** `SyncLog`

**History Tables:** `AttendanceAuditLog`, `AttendanceActivityLog`

#### 4. Key Findings
- `notifications.py` in attendance app is **83 bytes — empty placeholder**. Notification types `check_in`, `late`, `missing` registered in `Notification.notif_type` but **never dispatched**.
- `SyncLog` has no FK to failed records — only aggregate counts. Cannot trace which records failed.
- `is_policy_exception` field on Attendance has **no audit trail for who set it**.
- `AttendanceActivityLog` and `AttendanceAuditLog` are module-local, not wired to global systems.
- WiFi IP validation (`Branch.wifi_ip`) exists as a field but **is never enforced in code**.

#### 5. Missing Features
- ❌ Late/absent/forgot-checkout → Notification dispatch
- ❌ Unified logging to global ActivityLog/AuditLog
- ❌ Per-employee attendance trend charts
- ❌ Department-level attendance breakdown
- ❌ OT trend report
- ❌ No biometric / QR code check-in
- ❌ No roster / shift scheduling per employee

PHASE 7 - WORKFLOW & NOTIFICATION ENGINE
================================================================================

REUSABLE WORKFLOW ENGINE:
  Registers: WorkflowDefinition (code, module, steps).
  Processes: WorkflowInstance per request object.
  Records  : WorkflowAction per step (approve/reject/return/escalate).

UNIVERSAL WORKFLOW STATES:
  draft, pending_step_1, pending_step_2, pending_step_3,
  approved, rejected, returned, cancelled, escalated.

STATE TRANSITIONS:
  draft             -> pending_step_1  (submitter action)
  pending_step_1    -> pending_step_2  (approver 1 approves)
  pending_step_1    -> rejected        (approver 1 rejects)
  pending_step_1    -> returned        (approver 1 returns)
  pending_step_2    -> pending_step_3  (approver 2 approves; if 3-step)
  pending_step_2    -> approved        (approver 2 approves; if 2-step)
  pending_step_2    -> rejected        (approver 2 rejects)
  pending_step_2    -> returned        (approver 2 returns)
  pending_step_3    -> approved        (approver 3 approves)
  pending_step_3    -> rejected        (approver 3 rejects)
  returned          -> pending_step_N  (submitter corrects and resubmits)
  any               -> escalated       (SLA breach auto-escalation)

SLA ENFORCEMENT:
  - Background job every 15 minutes.
  - Checks open WorkflowInstances where sla_deadline < now.
  - Sends escalation notification to escalation_role.
  - Sets status = escalated.
  - Logs WorkflowAction(action=escalate).

DELEGATION:
  - WorkflowDelegation checked before routing to approver.
  - Active delegation found -> route to delegate.
  - Delegation logged in WorkflowAction.delegated_by_id.

NOTIFICATION DISPATCH FUNCTION:
  dispatch(notif_type, actor, target_object, recipients, channels, metadata)
  -> Creates Notification rows (in-app).
  -> Sends email if channels includes email.
  -> Queues SMS if channels includes sms.
  -> Queues push if channels includes push.
  -> Always creates ActivityLog row.
  -> If notif_type in audit_trigger_list -> creates AuditLog row.

AUTO ACTIONS (SCHEDULED BACKGROUND JOBS):
  auto_absent_mark       : Daily 11:59 PM - all active employees.
  auto_ot_remind         : Daily 9:00 AM  - unapproved OT > 48h.
  auto_document_expiry   : Daily 8:00 AM  - 30/15/7 day thresholds.
  auto_probation_remind  : Daily 8:00 AM  - 14 days before end.
  auto_backup            : Configurable cron (daily or 3-day).
  auto_retention_cleanup : Weekly Sunday 2:00 AM - attendance > 3 months.
  workflow_sla_check     : Every 15 minutes.

PHASE 9 - SCALABILITY BLUEPRINT
================================================================================

CURRENT PERFORMANCE RISKS:
  RISK-01  SQLite single-writer limitation.
           Impact: >20 concurrent writers -> lock contention -> 500 errors.
           Mitigation: PostgreSQL migration before >50 users.

  RISK-02  O(n2) OrgHierarchyService.get_org_analytics().
           Impact: Degrades to seconds at >500 employees.
           Mitigation: Materialized path or recursive CTE. Cache result.

  RISK-03  admin_panel/views.py monolith (137,806 bytes).
           Impact: Deploy risk, merge conflicts, maintenance cost.
           Mitigation: Split by domain (Phase C).

  RISK-04  No background job queue (Celery/RQ).
           Impact: PDF generation, backup, email block the HTTP request.
           Mitigation: Celery + Redis before >100 users.

  RISK-05  No query-level caching beyond LeaveType (5-min TTL).
           Impact: Dashboard loads N+1 queries every request.
           Mitigation: Redis cache for dashboard aggregates.

  RISK-06  File storage is local filesystem.
           Impact: No HA, no CDN, lost on server failure.
           Mitigation: S3/GCS/Azure Blob for media files.

  RISK-07  SyncLog does not store failed UUID list.
           Impact: Cannot replay or identify failed offline records.
           Mitigation: Add failed_uuids JSON field (included in data model).

SCALABILITY ESTIMATES:

  TIER: 100 USERS (Current target)
    Database    : SQLite WAL (current) - acceptable.
    Web Server  : Single Gunicorn, 4 workers.
    File Storage: Local filesystem (acceptable).
    Caching     : None required.
    Background  : Management commands via cron (current) - acceptable.
    Risk        : O(n2) hierarchy noticeable if >200 employees.

  TIER: 1,000 USERS
    Database    : PostgreSQL (mandatory). PgBouncer connection pooling.
    Web Server  : 2 Gunicorn behind Nginx load balancer.
    File Storage: S3-compatible (MinIO or AWS S3).
    Caching     : Redis - Django cache + sessions.
    Background  : Celery + Redis (PDF, email, backup, cron).
    Indexes     : Full index audit and optimisation.
    Risk        : Dashboard aggregation queries need 5-min cache.

  TIER: 10,000 USERS
    Database    : PostgreSQL + read replicas. Attendance partitioned by month.
                  ActivityLog/AuditLog archival strategy.
    Web Server  : Horizontal scaling + auto-scaling group.
    File Storage: AWS S3 + CloudFront CDN.
    Caching     : Redis cluster. Per-user permission cache in Redis.
    Background  : Celery cluster, multiple queues (critical/normal/bulk).
    Search      : Elasticsearch for employee/audit search.
    API         : Rate limiting (100 req/min), API gateway.
    Risk        : AuditLog to millions of rows - partition by month.

  TIER: 100,000 USERS
    Architecture: Microservices per domain.
    Message Bus : Apache Kafka for event streaming.
    Database    : Multi-region PostgreSQL cluster. CQRS for reports.
    API Gateway : Kong or AWS API Gateway.
    Search      : OpenSearch cluster.
    Monitoring  : DataDog / Prometheus + Grafana.
    NOTE: Requires full architectural redesign. Not in current roadmap.

CRITICAL INDEXES (must exist before >100 users):
  Attendance(employee_id, date)              - composite, most frequent query.
  Attendance(date, status, is_expired)       - dashboard aggregations.
  LeaveRequest(employee_id, status)          - pending count queries.

  Employee(status, branch_id, department_id) - HR dashboard aggregations.

ENGINEERING RULES (STANDING ORDERS)
================================================================================

ENG-01  Never put business logic in models.save() or models.delete().
        Use service classes in apps/<module>/services.py.

ENG-02  Every state transition must write an immutable history/audit record.

ENG-03  Every approval action must call the Workflow Engine.
        No direct status field updates from views.

ENG-04  Every notification must go through notifications.dispatch.
        log_activity() or notifications.dispatch.send_notification().

ENG-05  Never hardcode role names in views. Always use PermissionEngine.evaluate()
        with permission codenames.

ENG-06  All background tasks must be idempotent and safe to re-run.

ENG-07  All file uploads must validate extension AND size at the model/form level.

ENG-08  All sensitive credentials loaded from environment variables.
        Never commit credentials to source control.

ENG-09  All new tables must include created_at, updated_at (or created_at only
        for append-only/immutable tables).

ENG-10  sync_uuid must be present on any model that participates in offline sync.
        sync_uuid must be UNIQUE and UUID4 generated client-side.

ENG-11  AuditLog records are INSERT only. No UPDATE. No DELETE ever.

ENG-12  EmploymentHistory records are INSERT only. No UPDATE. No DELETE ever.

ENG-13  All dashboard aggregation queries must be wrapped in try/except and
        fall back to zero counts. Never raise 500 on a dashboard load.

ENG-14  No view file exceeds 500 lines. Split by domain when approaching limit.

ENG-15  Permission cache (_resolved_permissions_cache) must be cleared when
        roles or overrides are changed for a user.
